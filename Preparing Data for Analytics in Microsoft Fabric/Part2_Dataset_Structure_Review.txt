PART 2 - ORGANIZE AND STRUCTURE THE ANALYTICS-READY DATASET

SCOPE OF THIS REVIEW
The two tables imported in Part 1 were profiled in place using the SQL analytics
endpoint. No data was modified. Every figure quoted below is a query result, and
the query that produced it is shown so the finding can be reproduced.

  Tables reviewed:  sales_raw   5,025 rows, 5 columns
                    customers     515 rows, 4 columns

--------------------------------------------------------------------------------
1. FACT-LIKE TABLES
--------------------------------------------------------------------------------

sales_raw is the only fact-like table in this Lakehouse.

Tests applied and results:

  Test 1 - Does the grain correspond to a business event?
    Yes. One row represents one sales transaction. The table answers "what
    happened", not "what something is".

  Test 2 - Does it contain additive measures?
    Yes, one: amount. It can be summed across customer, region and time and the
    result remains meaningful. This is the defining property of a fact table.

  Test 3 - Does it contain a time anchor?
    Yes: transaction_date, spanning 2024-01-01 to 2025-12-31. Two complete years
    means year-over-year comparison is possible without a partial period.

  Test 4 - Does it hold foreign keys pointing outward?
    Yes: customer_id references the customers table. The column identifies a
    related entity rather than describing anything itself.

  Test 5 - Does row count scale with activity rather than with entity count?
    Yes. 5,025 transaction rows against 500 distinct customers, an average of
    roughly 10 transactions per customer. The table grows as trading continues.

  Conclusion: sales_raw is the central fact table of the star schema.

Grain statement (the single most important line of this review):
  One row per sales transaction, identified by transaction_id.

This statement is currently FALSE for the table as loaded. See risk 1.

--------------------------------------------------------------------------------
2. DIMENSION-LIKE TABLES
--------------------------------------------------------------------------------

customers is the only dimension-like table present.

Tests applied and results:

  Test 1 - Is the grain one row per entity rather than per event?
    Intended yes, actual NO. 515 rows describe 500 distinct customers. See
    risk 1.

  Test 2 - Are the non-key columns descriptive attributes?
    Yes. customer_name, customer_segment and region all answer "who is this
    customer", not "what did they do".

  Test 3 - Are there additive measures?
    No. Nothing in this table can meaningfully be summed. Correct for a
    dimension.

  Test 4 - Does it supply grouping and filtering labels?
    Yes. customer_segment and region are the axes that revenue will be sliced
    by. This is the table's entire purpose - it gives the fact table meaning.

  Test 5 - Does it change slowly?
    Yes. Customer attributes change by correction or re-registration, not with
    every transaction.

  Conclusion: customers is a dimension table, subject to the qualification in
  risk 1.

MISSING DIMENSIONS
Two dimensions that a production model would need are absent and should be
noted as a structural gap rather than a data quality defect:

  Date dimension - there is no dim_date. Without one, reporting is limited to
    whatever the transaction_date column can express. Fiscal periods, holiday
    flags, week numbering and "same period last year" logic all require a
    generated calendar table. Recommendation: build dim_date covering
    2024-01-01 to 2025-12-31 as part of the curated layer.

  Region dimension - region exists as free text in two tables with 31 distinct
    spellings (see risk 5) and no authoritative list of valid values. It should
    become a small conformed dimension with five rows, so that a region either
    exists or does not, rather than being whatever string was typed.

There is no product, store or channel dimension because the source data carries
no such columns. Revenue can be analysed by customer, segment, region and time,
and by nothing else. This is a scope limit that should be communicated to the
reporting team before dashboard requirements are agreed.

--------------------------------------------------------------------------------
3. JOIN KEYS
--------------------------------------------------------------------------------

PRIMARY JOIN

  customers.customer_id  (1) ----< sales_raw.customer_id  (many)

  Cardinality intended:  one-to-many
  Cardinality observed:  many-to-many - the join is not safe as written
  Join type recommended: LEFT JOIN from sales_raw to customers, so that
                         transactions with no matching customer remain visible
                         instead of disappearing

  Verification query:
    SELECT (SELECT COUNT(*) FROM sales_raw)              AS fact_rows,
           (SELECT COUNT(*) FROM customers)              AS dim_rows,
           (SELECT COUNT(DISTINCT customer_id) FROM customers) AS dim_keys,
           COUNT(*)                                      AS joined_rows
    FROM   sales_raw s
    JOIN   customers c ON s.customer_id = c.customer_id;

  Result:
    fact_rows    5,025
    dim_rows       515
    dim_keys       500
    joined_rows  5,295

  A join returning more rows than the fact table is proof that the key is not
  unique on the dimension side. This single query is the fastest way to detect
  the problem and should be run before any join is trusted.

DEGENERATE / CONFORMED KEY

  sales_raw.region  and  customers.region

  These are not a join key and must not be used as one. They are two independent
  attributes that happen to share a name and a domain. Joining on region would
  produce a cartesian explosion and a meaningless result. Their relationship is
  a consistency check, not a relationship in the model:

    SELECT COUNT(*) AS disagreeing_rows
    FROM   sales_raw s
    JOIN   customers c
      ON   UPPER(TRIM(s.customer_id)) = UPPER(TRIM(c.customer_id))
    WHERE  UPPER(TRIM(s.region)) <> UPPER(TRIM(c.region))
      AND  TRIM(s.region) <> '' AND TRIM(c.region) <> ''
      AND  LENGTH(TRIM(s.region)) > 1;

  Result: 319 rows where the transaction region differs from the customer's
  assigned region. See risk 5.

DEGENERATE DIMENSION

  sales_raw.transaction_id is a degenerate dimension - a key that lives in the
  fact table with no dimension table behind it. It carries no attributes, but it
  is essential for auditing and for deduplication, and it must not be dropped
  when the curated fact table is built.

ABSENT KEY

  There is no date key. transaction_date is a raw string, not a foreign key to a
  calendar table. Once dim_date exists, the fact table should carry a date_key
  joining to it.

--------------------------------------------------------------------------------
4. HOW THE DATASETS SUPPORT ANALYTICS AND REPORTING WORKFLOWS
--------------------------------------------------------------------------------

STRUCTURAL FIT
The two tables form a minimal star schema: one fact surrounded by one dimension.
This shape is what Power BI and the Fabric semantic model are optimised for. The
engine can filter the dimension, propagate the filter down the one-to-many
relationship to the fact table, and aggregate the measure - the standard pattern
behind almost every dashboard visual.

QUESTIONS THE MODEL CAN ANSWER ONCE CURATED

  By customer      revenue per customer, transaction frequency, average order
                   value, top-N customer ranking, customers with no activity in
                   a period
  By segment       revenue contribution by Consumer / Corporate / Small Business
                   / Enterprise, average order value by segment, segment mix
                   shifting over time
  By region        revenue and transaction volume by region, regional share of
                   total, regional growth rates
  By time          monthly and quarterly trend, year-over-year 2024 vs 2025,
                   seasonality, moving averages
  Combined         segment performance within region, month-over-month movement
                   for a single segment, cohort behaviour by first purchase date

REPORTING WORKFLOWS SUPPORTED IN FABRIC
The Lakehouse serves the same Delta files to three consumption paths without
copying data:

  SQL analytics endpoint  ad-hoc T-SQL investigation, and the source for
                          paginated or embedded reporting
  Default semantic model  direct Power BI report building with Direct Lake mode,
                          which reads the Delta files without import or refresh
  Spark notebooks         profiling, validation and the transformations that
                          build the curated layer

Direct Lake is the significant one for this project: reports read the Parquet
files directly, so a corrected value in the curated table is visible in the
report without a dataset refresh. That is an advantage only if the underlying
table is correct - it also means an error propagates to every report instantly,
with no refresh cycle acting as a buffer.

WHAT THE MODEL CANNOT SUPPORT
  - Product or category analysis. No product columns exist.
  - Basket or line-item analysis. The grain is the transaction, not the line.
  - Margin or profitability. Only revenue is captured, no cost.
  - Channel comparison. No channel column exists.
  - Customer history over time. The dimension holds current attributes only,
    with no effective dates, so a customer who changed segment appears always to
    have been in the current one. If historical accuracy matters, the dimension
    needs Type 2 slowly-changing treatment.

PRECONDITION
Every workflow above assumes the join is safe and the measure is numeric.
Neither holds today. The tables support these workflows structurally but not yet
reliably, which is the distinction section 5 addresses.

--------------------------------------------------------------------------------
5. ANALYTICAL RISKS TO REPORTING RELIABILITY
--------------------------------------------------------------------------------

Five risks were identified. Each is stated with the evidence that found it, the
effect on reporting, and a recommended treatment. Severity reflects the chance
that the issue produces a wrong number that nobody notices.

................................................................................
RISK 1 - DUPLICATE JOINS                                       SEVERITY: CRITICAL
................................................................................

Finding
  customers contains 515 rows for 500 distinct customer_id values. 15 customer
  ids appear twice, with drifted attributes on the second row - a different
  segment, sometimes a different region - consistent with re-registration rather
  than an exact duplicate.

  Query:
    SELECT customer_id, COUNT(*) AS row_count
    FROM   customers
    GROUP  BY customer_id
    HAVING COUNT(*) > 1;
  Result: 15 rows returned.

  Separately, sales_raw contains 5,025 rows for 5,000 distinct transaction_id
  values - 25 transactions recorded twice.

  Query:
    SELECT COUNT(*) AS total, COUNT(DISTINCT transaction_id) AS distinct_ids
    FROM   sales_raw;
  Result: 5,025 and 5,000.

Effect on reporting
  The duplicate dimension rows cause fan-out: each transaction belonging to an
  affected customer is matched twice and counted twice. The duplicated customers
  are disproportionately high-volume buyers, so the distortion is concentrated
  in exactly the customers a top-N report would highlight. Joined row count rises
  to 5,295 against a 5,025-row fact table. Transaction counts, revenue totals and
  customer rankings are all overstated, and the error is invisible in the report
  itself - the numbers look plausible.

  The 25 duplicate transactions inflate revenue independently of the join.

Treatment
  Deduplicate the dimension to one row per customer before it is used, choosing
  the surviving record by an explicit rule rather than arbitrarily. Deduplicate
  the fact table on transaction_id. Enforce the grain going forward with a
  validation step that fails the load if COUNT(*) <> COUNT(DISTINCT key).

................................................................................
RISK 2 - INCONSISTENT KEYS                                     SEVERITY: HIGH
................................................................................

Finding
  175 rows of sales_raw - 3.5% - do not match any customer record on an exact
  string comparison.

  Query:
    SELECT COUNT(*) AS unmatched
    FROM   sales_raw s
    LEFT   JOIN customers c ON s.customer_id = c.customer_id
    WHERE  c.customer_id IS NULL;
  Result: 175.

  Breaking that down by cause:

    Cause                          Rows   Example         Recoverable
    -----------------------------  -----  --------------  -----------
    Lowercased key                   60   cust-00042      yes
    Leading or trailing whitespace   40   "CUST-00042 "   yes
    Zero padding lost                30   CUST-42         yes
    No such customer exists          45   CUST-93817      no

  After normalising case, whitespace and padding, only 45 rows are genuinely
  unmatchable. 130 of the 175 are recoverable.

Effect on reporting
  An INNER JOIN silently drops all 175 rows. Revenue is understated, and the
  loss is silent - no error is raised and no row count warns the analyst. Worse,
  the loss is not random: it removes whichever customers happen to have been
  entered inconsistently, so regional or segment totals are skewed by an unknown
  amount rather than uniformly reduced.

  The 130 recoverable rows and the 45 true orphans require different responses,
  and treating them as one group leads to the wrong decision either way.

Treatment
  Normalise the key on both sides before joining:
    CONCAT('CUST-', LPAD(SPLIT(UPPER(TRIM(customer_id)), '-')[1], 5, '0'))
  Retain the 45 true orphans in the fact table with an is_orphan flag and an
  "Unknown customer" dimension member, so their revenue still appears in totals
  and the gap is visible rather than hidden. Raise the 45 with the source system
  owner - they indicate either a deleted customer record or a broken export.

................................................................................
RISK 3 - INCOMPLETE CUSTOMER RECORDS                           SEVERITY: MEDIUM
................................................................................

Finding
  Query:
    SELECT SUM(CASE WHEN customer_name IS NULL OR customer_name = ''
                    THEN 1 ELSE 0 END) AS missing_name,
           SUM(CASE WHEN customer_segment IS NULL OR customer_segment = ''
                    THEN 1 ELSE 0 END) AS missing_segment,
           SUM(CASE WHEN region IS NULL OR region = ''
                    THEN 1 ELSE 0 END) AS missing_region
    FROM   customers;

  Result:  missing_name 15,  missing_segment 18,  missing_region 11.

Effect on reporting
  Missing segment is the most damaging of the three. A "revenue by segment"
  visual will render a blank or (Blank) category, and segment percentages will
  not sum to the reported total - the classic symptom that erodes trust in a
  dashboard even when the underlying total is correct. Missing region has the
  same effect on regional reporting. Missing name affects presentation rather
  than arithmetic, but makes customer-level output unreadable.

Treatment
  Replace blanks with an explicit "Unknown" member rather than leaving them
  empty. An Unknown bucket is honest and forces the gap into the open; a blank
  looks like a rendering fault and invites the analyst to filter it away, which
  quietly removes real revenue from the total.

................................................................................
RISK 4 - INVALID AGGREGATIONS                                  SEVERITY: CRITICAL
................................................................................

Finding
  amount did not load as a numeric column. Profiling it:

    Query:
      SELECT COUNT(*) AS total_rows,
             SUM(CASE WHEN amount = '' THEN 1 ELSE 0 END) AS blank,
             SUM(CASE WHEN TRY_CAST(amount AS DECIMAL(12,2)) IS NULL
                       AND amount <> '' THEN 1 ELSE 0 END) AS uncastable,
             SUM(CASE WHEN TRY_CAST(amount AS DECIMAL(12,2)) < 0
                       THEN 1 ELSE 0 END) AS negatives,
             MAX(TRY_CAST(amount AS DECIMAL(12,2))) AS max_amount
      FROM   sales_raw;

    Result:
      total_rows  5,025
      blank          40
      uncastable     25   values such as $340.00, 1,250.06, 780.00 USD
      negatives      30
      max_amount 999,999.99

  Six rows carry values above 40,000, contributing roughly 1.37 million between
  them - consistent with decimal-point or units data-entry error rather than
  genuine large sales.

  The three revenue figures the table can produce:

    Query                                            Result
    ---------------------------------------------    ----------------
    SUM(amount) as loaded                            2,903,501.82
    SUM(amount) through the naive join               3,031,919.72
    SUM after dedupe, cast and outlier removal       1,533,214.74

Effect on reporting
  Revenue as loaded overstates the true figure by approximately 90%, and through
  the join by approximately 98%. Any dashboard built on the table today would be
  close to double the real number.

  Beyond the headline, three separate mechanisms distort averages:
    - 65 rows cast to NULL. SUM ignores them silently, so COUNT(*) is 5,025 but
      COUNT(amount) is 4,960. Average order value computed as SUM/COUNT(*)
      differs from AVG(amount), and both will be quoted as correct.
    - 30 negative amounts are refunds netted into revenue with no flag, so gross
      and net revenue cannot be reported separately.
    - 6 outliers dominate any average or maximum they are included in.

Treatment
  Cast explicitly with TRY_CAST and quarantine the failures rather than letting
  them become NULL unnoticed. Flag refunds and outliers with boolean columns
  instead of deleting them, so the exclusion is auditable and reversible. Define
  in the semantic model whether the published revenue measure is gross or net,
  and name the measure accordingly.

................................................................................
RISK 5 - INCONSISTENT FILTERING BEHAVIOUR                      SEVERITY: HIGH
................................................................................

Finding
  region in sales_raw holds 31 distinct string values representing 5 actual
  regions.

    Query:
      SELECT COUNT(DISTINCT region) AS distinct_literals FROM sales_raw;
    Result: 31.

  The variants observed: case differences (North / north / NORTH), leading and
  trailing whitespace, single-letter codes (N, S, E, W, C - 86 rows), and 30
  blanks. customers carries the same problem on a smaller scale: 22 rows with
  case or whitespace variants and 11 blanks.

  The consequence for filtering:

    SELECT SUM(CASE WHEN region = 'North' THEN 1 ELSE 0 END)              AS exact,
           SUM(CASE WHEN UPPER(TRIM(region)) = 'NORTH' THEN 1 ELSE 0 END) AS trimmed,
           SUM(CASE WHEN UPPER(TRIM(region)) IN ('NORTH','N') THEN 1 ELSE 0 END) AS with_codes
    FROM   sales_raw;

  The three columns return three different numbers from the same table for what
  a business user would call the same question.

  Separately, 319 joined rows have a transaction region that disagrees with the
  customer's assigned region.

Effect on reporting
  A slicer built on the raw column offers 31 options where the business
  recognises 5, and each option filters a partial slice. Two analysts asking
  "what was revenue in the North region" will get different answers depending on
  whether they filtered sales_raw.region or customers.region, and on how they
  handled casing - and both answers are defensible, which is what makes this
  dangerous. Regional totals will not reconcile to the company total, because
  blank and variant rows fall outside every filter.

Treatment
  Standardise to five canonical values, expanding single-letter codes and mapping
  blanks to "Unknown". Then resolve the definitional question explicitly: rename
  the two columns to sale_region and home_region in the curated layer so the
  distinction is visible in the name, and have the business state which one the
  official regional revenue measure uses. This is a governance decision, not a
  technical one, and it must be recorded rather than assumed.

................................................................................
SECONDARY FINDING - DATE PARSING                               SEVERITY: MEDIUM
................................................................................

  transaction_date also failed to load as a date type. 35 rows use dd/MM/yyyy
  instead of yyyy-MM-dd, and 15 rows are blank. A single-format TO_DATE() call
  nulls the 35 non-conforming rows and quietly drops them from every period
  filter and time-series visual.

  Treatment: parse with a COALESCE over both formats, and quarantine the 15
  blanks rather than allowing them to become NULL dates that silently vanish
  from trend reporting.

--------------------------------------------------------------------------------
6. REVIEW OUTCOME AND RECOMMENDATION
--------------------------------------------------------------------------------

RISK SUMMARY

  Risk                              Severity   Rows affected   Silent?
  --------------------------------  ---------  --------------  -------
  1  Duplicate joins                CRITICAL   15 dim, 25 fact  yes
  2  Inconsistent keys              HIGH       175              yes
  3  Incomplete customer records    MEDIUM     44               partly
  4  Invalid aggregations           CRITICAL   101 + all sums   yes
  5  Inconsistent filtering         HIGH       443              yes
  -  Date parsing                   MEDIUM     50               yes

"Silent" is the column that matters. Every one of these failures produces a
plausible-looking number rather than an error. Nothing in the current tables
would alert an analyst that a report is wrong.

RECOMMENDATION: DO NOT APPROVE sales_raw AND customers FOR DIRECT REPORTING USE.

The tables are structurally sound - the star schema is correct, the fact and
dimension roles are unambiguous, and the join key is identifiable. The problems
are in the data, not the design, and all of them are fixable. But a report built
on the tables as they stand would overstate revenue by roughly 90%, and would do
so convincingly.

Approve instead a curated layer built on top of them:

  dim_customer   one row per normalised customer key, blanks replaced with
                 Unknown, regions standardised, renamed home_region
  dim_date       generated calendar covering 2024-01-01 to 2025-12-31
  dim_region     five canonical regions plus Unknown
  fact_sales     deduplicated on transaction_id, amount cast with TRY_CAST,
                 dates parsed from both formats, regions standardised and
                 renamed sale_region, with is_orphan / is_refund / is_outlier
                 flags preserving rather than deleting the problem rows

Point the semantic model at the curated tables and leave the raw tables in the
Lakehouse for lineage. Expose the raw tables to no one but the engineering team.

ACCEPTANCE TESTS BEFORE THE CURATED LAYER IS APPROVED

  1. COUNT(*) = COUNT(DISTINCT customer_key) in dim_customer          expect 500
  2. COUNT(*) = COUNT(DISTINCT transaction_id) in fact_sales          expect 5,000
  3. Joined row count equals fact row count - no fan-out              expect 5,000
  4. Rows failing the customer join, after normalisation              expect 45
  5. COUNT(DISTINCT sale_region) in fact_sales                        expect 6
     (five regions plus Unknown)
  6. Revenue excluding refunds and outliers                           expect 1,533,214.74
  7. Rows with an unparseable date                                    expect 15, all quarantined

Test 3 is the one that proves the model is safe to report on. Test 6 is the
number the business should be shown. If a future load changes either, the load
should fail rather than publish.
